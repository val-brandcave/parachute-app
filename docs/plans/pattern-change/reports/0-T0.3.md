## Deviations

1. **Spend is applied in time order** (the spec text says only "purchased first"). A pool model would retroactively move spend onto packs bought later. That would contradict each debit's recorded `paidFrom` and make a trial user who later buys a pack look as if all 6 trial credits were never touched. The task's named test case passes under both models.
2. **`autoReloadDue` is called from the store, not from `TopUpModal`.** The store's `debitForReview` is the only place a reload fires, which is the one rule. TopUpModal now reads and writes the same `AUTO_RELOAD_DEFAULTS` (pack, threshold, cap), but it has no point where a "due" check means anything. Calling it there would be contrived.
3. **Invoiced orgs always get `lowTone: "ok"`.** They are billed outside the wallet. This is not in the stub's comment.
4. **`walletView.runwayDays` is computed but not yet read by the UI.** `OverviewTab` and `WalletCard` still draw the runway from `useUsage`/`buildUsageLines`, which anchor to the demo date (`DEMO_TODAY`/`usageAnchor`). Switching them to real `now` would move the seeded numbers. Only the low tone moved to `walletView`, as the task asks.
5. **`WalletCard` lost its runway amber** (`runwayWarn` under 7 days). PC-18 says low tone keys off the balance only. In that branch `lowTone` is always `"ok"`, because a low balance takes the Low card first.
6. **`billing-data.spendOrderSentence(grants)` keeps its signature** because `BalanceCard.tsx` (not my file) calls it. It now wraps the lib sentence. The two exports share a name; the barrel re-exports only the billing-data one.
